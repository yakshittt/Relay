# RELAY Security & Threat Model

## 1. Security Architecture Principles

RELAY enforces zero-trust boundaries between:
1. **The Voice LLM Layer**: The LLM is an untrusted natural language parser. It cannot directly execute shell commands, run arbitrary HTTP queries, or provide a simple boolean flag to bypass approval.
2. **The IoT Device Tier**: ESP32 probes possess only telemetry ingestion authority via dedicated device tokens; they cannot query incidents or trigger recoveries.
3. **The Operator / Management Tier**: Protected by Bearer authentication, audit logging, and single-use cryptographic tokens.
4. **Physical Network Hardware (Jio Router)**: Probed strictly as an external black-box target over LAN. No firmware modification or unauthenticated admin commands are ever executed.

---

## 2. Authentication & Authorization Boundaries

### Bearer Token Authentication
- Private endpoints (`/v1/tools/*`, `/v1/sites/*`, `/v1/overview/*`, `/v1/demo/*`) require an `Authorization: Bearer <TOKEN>` header.
- Validated using constant-time string comparison (`secrets.compare_digest`) to prevent timing side-channel attacks.

### Device Telemetry Authentication
- IoT devices submit heartbeats via `POST /v1/devices/heartbeat` authenticated with an `X-Device-Token` header.
- Devices are restricted strictly to telemetry writes. They cannot access diagnostic probe outputs, read incident records, or trigger recovery actions.

### Multi-Step Action Authorization Flow
To prevent accidental or LLM-induced disruptions, recovery follows a 3-step authorization lifecycle:
1. **Proposal**: `/v1/tools/recovery/propose` validates that the action type is on the strict server-side allowlist.
2. **Token Issuance**: The server generates a high-entropy URL-safe token (`apr_<token>`) with a strictly enforced TTL (default 300 seconds) and records it in SQLite.
3. **Atomic Consumption**: When `/v1/tools/recovery/execute` is invoked, the token is validated and marked consumed in a database transaction (`is_consumed=1`). Replayed or duplicate requests are rejected.

---

## 3. SSRF & Target Allowlist Enforcement

To prevent Server-Side Request Forgery (SSRF) and intranet port scanning:
- Every diagnostic probe target is validated through `app/security/ssrf.py`.
- Targets must match the configured target allowlist (`ALLOWLISTED_HOSTS`).
- Malformed hostnames, embedded command characters (`;`, `|`, `` ` ``), and unsafe URL schemes (`file://`, `ftp://`, `gopher://`) are rejected with `SSRFValidationError`.
- Request timeouts are strictly bounded (e.g., 3.0s for HTTPS egress, 800ms for gateway checks) to prevent resource exhaustion attacks.

---

## 4. No Arbitrary Shell Execution

- RELAY does **not** invoke `subprocess.Popen` or `os.system` with parameters derived from user queries or LLM outputs.
- Probes use native Python sockets (`socket.getaddrinfo`, `socket.create_connection`) and `httpx`.
- Recovery adapters are hardcoded Python handlers registered in `ALLOWLISTED_ACTIONS`.

---

## 5. Audit Logging

Every security-sensitive operation is logged to the `audit_logs` SQLite table with UTC timestamp, actor identity, action type, and structured metadata:
- `INCIDENT_OPENED`
- `DEVICE_HEARTBEAT_RECEIVED`
- `RECOVERY_ACTION_PROPOSED`
- `RECOVERY_ACTION_COMPLETED`
- `UNAUTHORIZED_RECOVERY_ATTEMPT`

---

## 6. AI Incident Interpretation Security Boundaries & Secret Handling

The generative AI interpretation layer (`app/services/ai/`) provides explanatory synthesis and operator Q&A. To mitigate risks associated with prompt injection, model hallucination, and credential exfiltration, RELAY enforces a defense-in-depth model where AI components are treated as unprivileged:

1. **Strict Authentication & Access Control**:
   - The interpretation endpoint (`POST /v1/ai/interpret`) requires standard Bearer token authentication verified via `secrets.compare_digest`.
   - Incident records are loaded strictly from the server database (`storage.get_incident`). Callers cannot supply arbitrary probe checks or inject ungrounded telemetry data into the evidence payload.

2. **Non-Authoritative Recovery Boundary**:
   - The AI service has zero action execution authority. It has no tools, APIs, or credentials to execute diagnostic probes, formulate recovery proposals, issue cryptographic approval tokens (`apr_<token>`), or invoke recovery adapters.
   - The `recommended_action` field in the AI output is purely advisory narrative. Authoritative recovery remains governed by `app/services/recovery_policy.py` and requires human-confirmed, single-use approval tokens.

3. **Evidence Grounding & Citation Validation**:
   - Factual statements generated by the model are parsed into `GroundedFact` contracts and validated against genuine server probe results (`probe:*`) and sentinel device telemetry (`device:*`).
   - If the model generates a citation for an unknown, fabricated, or unverified probe (e.g. `probe:optical_fiber_power`), the validator automatically re-attributes the source to `unverified_model_claim`.
   - The Operations Console renders unverified claims with an alert badge to alert operators of unsubstantiated assertions.

4. **Targeted Credential Redaction & Sanitization**:
   - Before prompt construction, input queries and incident context pass through `_sanitize_for_prompt`, which scrubs known server secrets (`RELAY_API_TOKEN`, `DEVICE_TOKEN`, `AI_API_KEY`, and approval tokens matching `apr_[a-zA-Z0-9_\-]+`).
   - Upstream LLM provider credentials (`AI_API_KEY`) reside exclusively in environment variables and are never reflected in client responses or persistent incident timelines.
   - All structured model output fields (`summary`, `diagnostic_hypothesis`, `recommended_action`, `uncertainty_caveats`, and `grounded_facts[].statement`) undergo recursive redaction filtering prior to serialization.
   - *Security Note*: Pattern-based redaction is a defense-in-depth safeguard against accidental leakage; the fundamental security guarantee rests on the complete absence of privileged execution capabilities in the AI service.

5. **Defensive Parsing & Deterministic Fallback**:
   - The service defensively validates stored evidence structures, safely handling missing or null probe checks and malformed device dictionaries without unhandled exceptions.
   - If the upstream provider experiences network timeouts, HTTP errors (e.g. 429, 500), returns corrupted JSON, or if evidence is insufficient, the system immediately returns a deterministic, rule-grounded synthesis with `fallback_used: true`.

## 7. Security Limitations & Verification Scope

1. **Local vs. Live LLM Verification**: Unit tests cover provider error mapping and redaction using mock providers and mocked HTTP transport. Security properties against live external LLM endpoints (e.g. prompt injection resistance against specific proprietary models) have not been verified with live external credentials.
2. **Prompt Injection Boundary**: While prompt sanitization scrubs credentials and delimiters, no natural-language prompt filter can mathematically guarantee immunity against all semantic prompt injection techniques. The system's primary protection against prompt injection is architectural: even a compromised AI interpretation response cannot execute shell commands, alter network configurations, or bypass the recovery approval token requirement.
3. **Hardware Sentinel Security**: The physical ESP32 sentinel firmware relies on pre-shared device tokens over HTTP/HTTPS. In production, this channel requires TLS terminating at an authentic gateway or reverse proxy to prevent token interception on the local LAN.
